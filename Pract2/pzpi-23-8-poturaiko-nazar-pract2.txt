Метою роботи є дослідження архітектури складної програмної системи та
аналіз застосованих архітектурних підходів.
У межах практичного заняття необхідно:
1) обрати програмну систему для архітектурного аналізу;
2) дослідити її структурну організацію;
3) визначити використані архітектурні стилі;
4) описати основні компоненти та підсистеми;
5) проаналізувати взаємодію компонентів, потоки даних і протоколи;
6) оцінити масштабованість, надійність та підтримуваність системи;
7) підготувати презентацію та відеодоповідь тривалістю 10-12 хвилин;
8) використати створений у межах дисципліни GitHub-репозиторій;
9) оформити звіт відповідно до вимог дисципліни та ДСТУ 3008:2015.
Для аналізу обрано програмну систему OpenBSD - вільну багатоплатформну
операційну систему, орієнтовану на безпеку та криптографію. Вона є яскравим
прикладом сучасної монолітної архітектури з глибокою інтеграцією захисних
механізмів на рівні ядра та простору користувача.

3.2 Архітектурний стиль системи
Архітектуру OpenBSD доцільно розглядати як класичну монолітну
архітектуру операційної системи, що доповнена концепціями розділення привілеїв
та мінімізації прав доступу (див. рис 3.1).

Рисунок 3.1 – UML-діаграма взаємодії основних компонентів системи
Головні архітектурні підходи:
1) Монолітне ядро: ядро працює в єдиному адресному просторі з повними
привілеями, керуючи пам’яттю, процесами, файловими системами та мережевим
стеком.
2) Розділення привілеїв (privilege separation): застосунки в просторі
користувача розбиваються на кілька процесів. Один процес працює з правами
суперкористувача для виконання критичних операцій, а інші процеси виконують
основну роботу з правами непривілейованого користувача.

6
3) Відмовостійкість через простоту: розробники регулярно проводять аудит
коду для усунення складних і зайвих архітектурних конструкцій.
Обґрунтування такого підходу полягає в тому, що монолітне ядро забезпечує
найвищу швидкодію для мережевого стека, що є критичним для серверів, тоді як
жорстка ізоляція процесів на рівні користувача нівелює основні ризики безпеки.
3.3 Основні компоненти системи
Архітектура OpenBSD складається з таких базових компонентів:
1) Монолітне ядро: основа системи, яка керує апаратурою. Ядро містить
механізми захисту, такі як KARL (Kernel Address Randomized Link), що генерує
унікальне ядро при кожному завантаженні системи.
2) Packet Filter (PF): інтегрована в ядро підсистема фільтрації мережевого
трафіку. Вона відповідає за маршрутизацію, трансляцію адрес та балансування
навантаження.
3) Простір користувача (Userland): набір утиліт, бібліотек та системних служб.
Важливою частиною є власна реалізація стандартної бібліотеки C, яка містить
функції безпеки, що запобігають переповненню буфера.
4) Системні служби (Daemons): безпечні служби, що постачаються із
системою (OpenSSH, OpenHTTPd), побудовані за архітектурою ізоляції процесів.
3.4 Взаємодія компонентів
Взаємодія між простором користувача та ядром відбувається виключно через
системні виклики. Унікальною архітектурною особливістю OpenBSD є можливість
обмежувати доступні системні виклики для конкретних процесів за допомогою
механізму pledge.
Типовий потік взаємодії компонентів у системі:
1) Процес ініціалізується і викликає системний виклик pledge, повідомляючи
ядру, які класи викликів йому знадобляться у подальшому.

3.5 Масштабованість та надійність
Надійність є ключовою характеристикою архітектури OpenBSD. Вона
забезпечується на кількох рівнях: 1) Захист пам’яті: використання політики W^X
(Write XOR Execute). Сторінка пам’яті може бути або доступною для запису, або
доступною для виконання, але ніколи одночасно. 2) Рандомізація: технологія ASLR
застосовується не лише до прикладних програм, але й до самого ядра. 3) Ізоляція
файлової системи: використання системного виклику unveil дозволяє процесу мати
доступ лише до тих частин файлової системи, які необхідні йому для роботи.
Щодо масштабованості, система ефективно використовує симетричну
багатопроцесорність та дозволяє будувати масштабовані мережеві рішення за
допомогою PF, підтримуючи швидку обробку великих обсягів мережевих правил.

3.6 Приклади програмної реалізації
Програмна архітектура OpenBSD активно використовує системні виклики для
обмеження доступу. Наведемо базовий приклад використання механізмів ізоляції
мовою C, що демонструє, як процес обмежує власні права під час виконання.
int main() {
// Крок 1: Відкриваємо доступ лише до одного каталогу для
читання
if (unveil("/var/empty", "r") == -1) {
err(1, "unveil error");
}
// Крок 2: Блокуємо можливість подальших змін у файловій
системі
if (unveil(NULL, NULL) == -1) {
err(1, "unveil lock error");
}
// Крок 3: Залишаємо процесу лише права на базовий ввід/вивід
та читання
if (pledge("stdio rpath", NULL) == -1) {
err(1, "pledge error");
}
return 0;
}

Цей фрагмент ілюструє концепцію зменшення поверхні атаки: спочатку
процес ізолює себе у файловій системі за допомогою виклику unveil, а потім
назавжди відмовляється від усіх системних викликів, крім базового вводу/виводу
та дозволу на читання через pledge. Більш розгорнутий приклад із розділенням
привілеїв наведено у додатку В.
